# ความสามารถในการทำซ้ำ

ไลบรารีของ `rust-random` ให้คำมั่นแบบจำกัดเกี่ยวกับความสามารถในการทำซ้ำของ PRNG ที่ซีดได้และอัลกอริทึมแบบสโทแคสติก

บทนี้ว่าด้วยความเสถียรของค่าจากกระบวนการดีเทอร์มินิสติกที่ใช้ไลบรารีของ `rust-random`

## การเปลี่ยนแปลงที่ทำให้ API แตกหัก การเปลี่ยนแปลงค่าผลลัพธ์ และ SemVer

การเปลี่ยนแปลง (ของไลบรารี) ถือว่า**ทำให้ API แตกหัก** หากมันอาจทำให้โค้ดที่เข้ากันได้กับ API เวอร์ชันก่อนหน้าคอมไพล์ไม่ผ่าน หรือเป็นการเปลี่ยนแปลงที่เข้ากันไม่ได้ในลักษณะอื่น

เรามุ่งมั่นปฏิบัติตาม[กฎ SemVer](https://semver.org/) เกี่ยวกับการเปลี่ยนแปลงที่ทำให้ API แตกหักและเวอร์ชัน `MAJOR.MINOR.PATCH` กล่าวคือ หลังเวอร์ชัน 1.0 เวอร์ชันไมเนอร์ใหม่ไม่ควรนำการเปลี่ยนแปลงที่ทำให้ API แตกหักเข้ามา

การเปลี่ยนแปลงถือว่า**ทำให้ค่าผลลัพธ์เปลี่ยนแปลง** หากมันไม่ได้ทำให้ API แตกหัก แต่ทำให้ค่าเอาต์พุตของกระบวนการสโทแคสติกแบบดีเทอร์มินิสติกที่ใช้เฉพาะส่วนของ API `rust-random` ที่ไม่เปลี่ยนแปลงนั้นเปลี่ยนไป

การเปลี่ยนแปลงที่ทำให้ค่าผลลัพธ์เปลี่ยนแปลงสามารถทำได้ในเวอร์ชันไมเนอร์

## ไอเท็มดีเทอร์มินิสติกที่พอร์ตไม่ได้

ไอเท็มใน API ของ `rust-random` (เช่น struct หรือฟังก์ชัน) อาจถูกประกาศว่า**พอร์ตไม่ได้** หมายความว่ามันสละสิทธิ์ในการรับประกันความสามารถในการทำซ้ำทั้งหมด ไอเท็มที่พอร์ตไม่ได้อาจเป็นดีเทอร์มินิสติก แต่ให้ผลลัพธ์ที่แตกต่างกันบนแพลตฟอร์มและเวอร์ชันไลบรารีที่ต่างกัน (อาจมีการเปลี่ยนแปลงที่ทำให้ค่าผลลัพธ์เปลี่ยนไปในรีลีสใดก็ได้)

นี่เป็นการเปลี่ยนนโยบายที่มีผลกับ `rand` ตั้งแต่เวอร์ชัน `0.10` หรือ `1.0` (แล้วแต่รีลีสใดมาถึงก่อน) จนถึงเวอร์ชัน `0.9` ไอเท็มที่พอร์ตไม่ได้ไม่ได้รับอนุญาตให้ทำการเปลี่ยนแปลงที่ทำให้ค่าผลลัพธ์เปลี่ยนไปในรีลีสแพตช์

คำประกาศว่าพอร์ตไม่ได้นี้ต้องระบุไว้อย่างชัดเจนในเอกสาร ไอเท็มต่อไปนี้มีคำประกาศดังกล่าว:

-   [`rand::rngs::SmallRng`](https://docs.rs/rand/latest/rand/rngs/struct.SmallRng.html)
-   [`rand::rngs::StdRng`](https://docs.rs/rand/latest/rand/rngs/struct.StdRng.html)

## ไอเท็มที่พอร์ตได้

ไอเท็มบางอย่างไม่ใช่ดีเทอร์มินิสติกอย่างชัดเจน (เช่น [`rand::rng`]) ไอเท็มบางอย่างเป็นดีเทอร์มินิสติกแต่พอร์ตไม่ได้ (ตามข้างต้น) ส่วนอื่นๆ ทั้งหมดของ API สาธารณะของเครต `rust-random` (รวมถึง PRNG การแจกแจง และอัลกอริทึมสโทแคสติกอื่นๆ) คาดว่าจะพอร์ตได้:

-   ผลลัพธ์ควรทำซ้ำได้ข้ามแพลตฟอร์ม
-   ผลลัพธ์ควรทำซ้ำได้ข้ามรีลีสแพตช์
-   รีลีสไมเนอร์ รวมถึงหลังเวอร์ชัน 1.0 อาจทำการเปลี่ยนแปลงที่ทำให้ค่าผลลัพธ์เปลี่ยนไปกับไอเท็มที่พอร์ตได้ การเปลี่ยนแปลงดังกล่าวต้องมีเหตุผลที่หนักแน่นและควรระบุไว้อย่างชัดเจนใน CHANGELOG

### การทดสอบ

เราคาดว่าอัลกอริทึมสโทแคสติกที่พอร์ตได้ทั้งหมดจะทดสอบความเสถียรของค่าเอาต์พุตด้วยการทดสอบแบบเวกเตอร์อ้างอิงรูปแบบใดรูปแบบหนึ่ง

-   PRNG ควรทดสอบกับเวกเตอร์อ้างอิงเมื่อมีให้ใช้ ([ตัวอย่าง](https://github.com/rust-random/rngs/blob/master/rand_xoshiro/src/xoshiro256starstar.rs#L122))
-   อัลกอริทึมอื่นๆ ควรมีเวกเตอร์ทดสอบของตัวเองใน
    เทสต์ `value_stability` หรือเทสต์ลักษณะเดียวกัน ([ตัวอย่าง](https://github.com/rust-random/rand/blob/master/src/distr/bernoulli.rs#L226))

## การรองรับเวอร์ชันก่อนหน้า

เรามุ่งมั่นรองรับผู้ใช้เครต `rust-random` ที่ใช้เวอร์ชัน `MAJOR.MINOR` ก่อนหน้า เพื่อจุดประสงค์ด้านความสามารถในการทำซ้ำ โดย:

-   ให้การแก้ไขด้านความปลอดภัยเป็นเวอร์ชันแพตช์ในกรณีที่เหมาะสม
-   อำนวยความสะดวกในการพอร์ตย้อนกลับของการเพิ่มเติมที่เข้ากันได้จากเวอร์ชันเครตในอนาคต *เมื่อมีการร้องขอ*
-   การแก้ไขอื่นๆ อาจได้รับการพิจารณาให้พอร์ตย้อนกลับ แต่บ่อยครั้งไม่สามารถทำได้หากไม่ทำให้ API แตกหักหรือทำให้ค่าผลลัพธ์เปลี่ยนไป

## ข้อจำกัด

### ความสามารถในการพอร์ตของ usize

น่าเสียดายที่มีไอเท็มที่พอร์ตไม่ได้ฝังอยู่ที่หัวใจของภาษา Rust หนึ่งอย่าง นั่นคือ `usize` (และ `isize`) ตัวอย่างเช่น ขนาดของ `Vec` ว่างจะแตกต่างกันบนเป้าหมาย 32 บิตและ 64 บิต สำหรับการใช้งานส่วนใหญ่แล้วนี่ไม่ใช่ปัญหา แต่เมื่อต้องสร้างเลขสุ่มแบบพอร์ตได้ มันกลับสำคัญ

มีกฎง่ายๆ ดังนี้: หากต้องการความสามารถในการพอร์ต *ห้าม* สุ่มค่า `usize` หรือ `isize` โดยตรง

ตั้งแต่ `rand v0.9` ชนิดข้อมูล `isize` และ `usize` ไม่ได้รับการรองรับในส่วนต่างๆ มากมายของ API สาธารณะ รวมถึง [`StandardUniform`] ส่วน `usize` ได้รับการรองรับโดย [`SampleUniform`] และด้วยเหตุนี้ [`Rng::random_range`] จึงใช้การสุ่มแบบ `u32` ทุกครั้งที่เป็นไปได้เพื่อเพิ่มความสามารถในการพอร์ตให้สูงสุด

### ความสามารถในการพอร์ตของทศนิยม

ผลลัพธ์ของการคำนวณทศนิยมขึ้นอยู่กับโหมดการปัดเศษและรายละเอียดของการ implement โดยเฉพาะผลลัพธ์ของฟังก์ชันอดิศัย (transcendental) จะแตกต่างกันไปในแต่ละแพลตฟอร์ม ด้วยเหตุนี้ ผลลัพธ์ของการแจกแจงใน `rand_distr` ที่ใช้ `f32` หรือ `f64` อาจพอร์ตไม่ได้

เพื่อบรรเทา (หรือทำให้ซับซ้อนขึ้น) ข้อกังวลนี้ เราจึงเลือกใช้ `libm` แทนการ implement ฟังก์ชันอดิศัยเหล่านั้นจาก `std` ดู [ฟีเจอร์ของ rand_distr](crate-features.html#ฟีเจอรของ-rand_distr)
