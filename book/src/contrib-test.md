# การทดสอบ

Rand มียูนิตเทสต์จำนวนหนึ่ง แม้ว่ามันจะไม่ครอบคลุมทั้งหมดหรือสมบูรณ์แบบ (ยินดีรับการปรับปรุง) เราชอบที่จะมีเทสต์สำหรับฟังก์ชันใหม่ทุกอย่าง

แนวป้องกันด่านแรกของการทดสอบคือเพียงรัน `cargo test` จากไดเรกทอรีที่เหมาะสม เนื่องจาก Rand รองรับสภาพแวดล้อมแบบ `no_std` (core เท่านั้น), `core+alloc` และ `std` จึงสำคัญที่จะต้องทดสอบทั้งสามแบบ (ขึ้นอยู่กับว่าฟีเจอร์ใดใช้ได้กับโค้ดนั้น):

```sh
# Test using std:
cargo test
# Test using only core:
cargo test --tests --no-default-features
# Test using core + alloc (requires nightly):
cargo +nightly test --tests --no-default-features --features=alloc
```

อาจคุ้มค่าที่จะทดสอบกับฟีเจอร์แฟล็กอื่นๆ ด้วย:

```sh
cargo test --all-features
```

โปรดทราบว่าสิ่งนี้ทดสอบเฉพาะแพ็กเกจปัจจุบัน (กล่าวคือ ไลบรารี Rand หลักเมื่อรันจากระดับบนสุดของที่เก็บ) หากต้องการทดสอบไลบรารีอื่น ให้ `cd` ไปยังไดเรกทอรีของมัน

เราไม่แนะนำให้ใช้ตัวเลือก `--package` ของ Cargo เนื่องจากมันมี
[ปฏิสัมพันธ์ที่น่าประหลาดใจ](https://github.com/rust-lang/cargo/issues/5364)
กับตัวเลือก `--feature` และล้มเหลวเมื่อมีแพ็กเกจเวอร์ชันเดียวกันหลายตัวอยู่ใน build tree CI ใช้ `--manifest-path` ในการเลือกแพ็กเกจแทน ขณะที่ระหว่างการพัฒนา การใช้ `cd` นั้นง่ายกว่า

## การเขียนเทสต์

เทสต์อาจเป็นยูนิตเทสต์ภายในซับโมดูล `test` ตัวอย่างเอกสาร แอปพลิเคชันตัวอย่าง (ไดเรกทอรี `examples`) การทดสอบแบบผสานรวม (ไดเรกทอรี `tests`) หรือ benchmark (ไดเรกทอรี `benches`)

โปรดทราบว่า*เฉพาะ*ยูนิตเทสต์และการทดสอบแบบผสานรวมเท่านั้นที่คาดว่าจะผ่านในรูปแบบ `no_std` (core เท่านั้น) และ `core+alloc` นี่เป็นทางเลือกโดยเจตนา; โค้ดตัวอย่างควรกำหนดเป้าหมายเฉพาะกรณีทั่วไป (`std`) เท่านั้น

### ตัวสร้างเลขสุ่ม

บ่อยครั้งโค้ดทดสอบต้องมี RNG บางตัวไว้ใช้ทดสอบ แต่ไม่ต้องการ RNG ตัวใดตัวหนึ่งโดยเฉพาะ ในกรณีนี้เราชอบใช้ `::test::rng` ซึ่งเรียบง่าย เริ่มต้นได้เร็ว และเป็นดีเทอร์มินิสติก:

```rust,ignore
let mut rng = ::test::rng(528); // just pick some number
```

เทสต์หลายตัวเกี่ยวข้องกับคุณสมบัติที่*น่าจะ*เป็นจริง แต่ไม่แน่นอน เราชอบให้เทสต์เช่นนั้นเป็นดีเทอร์มินิสติกเพื่อหลีกเลี่ยงความล้มเหลวที่ไม่จริง
