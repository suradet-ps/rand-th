# ความสามารถในการทำซ้ำ

ไลบรารีในเครือ `rust-random` ให้การรับประกันอย่างจำกัดเกี่ยวกับความสามารถในการทำซ้ำ (reproducibility) ของตัวสร้าง PRNG ที่ซีดได้ และอัลกอริทึมเชิงสโทแคสติก

เนื้อหาในบทนี้จะอธิบายถึงเสถียรภาพของค่าผลลัพธ์ (value-stability) ที่ได้จากกระบวนการแบบดีเทอร์มินิสติกเมื่อใช้งานไลบรารี `rust-random`

## การเปลี่ยนแปลงที่ทำให้ API แตกหัก การเปลี่ยนแปลงค่าผลลัพธ์ และ SemVer

การเปลี่ยนแปลงโค้ดของไลบรารีจะถือว่า**ทำให้ API แตกหัก (API-breaking)** หากการเปลี่ยนแปลงนั้นส่งผลให้โค้ดที่เคยใช้งานได้กับ API เวอร์ชันก่อนหน้าเกิดข้อผิดพลาดในการคอมไพล์ หรือเป็นการเปลี่ยนแปลงที่ไม่สามารถเข้ากันได้ย้อนหลังในรูปแบบใดๆ

เรายึดมั่นปฏิบัติตาม[ข้อกำหนด SemVer](https://semver.org/) อย่างเคร่งครัดเกี่ยวกับการเปลี่ยนแปลงที่ทำให้ API แตกหักและรูปแบบเวอร์ชัน `MAJOR.MINOR.PATCH` กล่าวคือ เมื่อพ้นเวอร์ชัน 1.0 ไปแล้ว เวอร์ชันไมเนอร์ใหม่จะต้องไม่นำการเปลี่ยนแปลงที่ทำให้ API แตกหักเข้ามา

ในขณะที่การเปลี่ยนแปลงจะถือว่า**ส่งผลกระทบต่อค่าผลลัพธ์ (value-breaking)** หากการเปลี่ยนแปลงนั้นไม่ได้ทำให้โครงสร้าง API พัง แต่ทำให้ค่าเอาต์พุตที่ผลิตจากกระบวนการสโทแคสติกแบบดีเทอร์มินิสติกเปลี่ยนไป (แม้จะเรียกใช้เฉพาะส่วนของ API ใน `rust-random` ที่ไม่มีการแก้ไขก็ตาม)

การเปลี่ยนแปลงที่ส่งผลกระทบต่อค่าผลลัพธ์นี้ ได้รับอนุญาตให้เกิดขึ้นได้ในเวอร์ชันไมเนอร์

## ไอเท็มดีเทอร์มินิสติกที่พอร์ตไม่ได้

ไอเท็มบางรายการใน API ของ `rust-random` (เช่น struct หรือฟังก์ชัน) อาจได้รับการประกาศไว้อย่างชัดแจ้งว่า**พอร์ตไม่ได้ (non-portable)** ซึ่งหมายความว่าไอเท็มนั้นจะไม่มีการรับประกันความสามารถในการทำซ้ำใดๆ ทั้งสิ้น ไอเท็มที่พอร์ตไม่ได้ยังคงทำงานแบบดีเทอร์มินิสติก (ให้ผลลัพธ์เดิมบนเครื่องเดียวกัน) แต่อาจให้ค่าผลลัพธ์ที่แตกต่างกันเมื่อรันข้ามแพลตฟอร์ม หรือเมื่อเปลี่ยนเวอร์ชันของไลบรารี (โดยอาจเกิดการเปลี่ยนแปลงที่ส่งผลกระทบต่อค่าผลลัพธ์ในรีลีสใดๆ ก็ได้)

นี่คือนโยบายใหม่ที่จะมีผลบังคับใช้กับ `rand` ตั้งแต่เวอร์ชัน `0.10` หรือ `1.0` เป็นต้นไป (แล้วแต่ว่าเวอร์ชันใดจะเผยแพร่ออกมาก่อน) จากเดิมในเวอร์ชัน `0.9` ที่ไม่อนุญาตให้ไอเท็มที่พอร์ตไม่ได้ทำการเปลี่ยนแปลงค่าผลลัพธ์ในรีลีสแพตช์

คำประกาศเรื่องการไม่รับประกันการพอร์ตนี้ จะต้องระบุไว้อย่างชัดเจนในเอกสาร โดยไอเท็มที่มีคำประกาศดังกล่าว ได้แก่:

-   [`rand::rngs::SmallRng`](https://docs.rs/rand/latest/rand/rngs/struct.SmallRng.html)
-   [`rand::rngs::StdRng`](https://docs.rs/rand/latest/rand/rngs/struct.StdRng.html)

## ไอเท็มที่พอร์ตได้

ไอเท็มบางชนิดทำงานแบบนอนดีเทอร์มินิสติกอย่างชัดเจน (เช่น [`rand::rng`]) และบางชนิดเป็นดีเทอร์มินิสติกแต่พอร์ตไม่ได้ (ตามที่ระบุไว้ข้างต้น) ส่วนประกอบอื่นๆ ทั้งหมดใน API สาธารณะของเครต `rust-random` (รวมถึง PRNG การแจกแจง และอัลกอริทึมสโทแคสติกอื่นๆ) ล้วนคาดหวังให้สามารถพอร์ตได้อย่างสม่ำเสมอ:

-   ผลลัพธ์ต้องสามารถทำซ้ำได้เหมือนเดิมข้ามแพลตฟอร์ม
-   ผลลัพธ์ต้องสามารถทำซ้ำได้เหมือนเดิมข้ามรีลีสแพตช์
-   รีลีสไมเนอร์ (รวมถึงหลังเวอร์ชัน 1.0) อาจมีการเปลี่ยนแปลงที่ส่งผลกระทบต่อค่าผลลัพธ์สำหรับไอเท็มที่พอร์ตได้ แต่การเปลี่ยนแปลงดังกล่าวจะต้องมีเหตุผลรองรับที่หนักแน่นเพียงพอ และต้องระบุไว้อย่างชัดเจนใน CHANGELOG

### การทดสอบ

เราคาดหวังให้อัลกอริทึมสโทแคสติกที่พอร์ตได้ทั้งหมด ผ่านการทดสอบเสถียรภาพของค่าเอาต์พุตโดยใช้เวกเตอร์ทดสอบอ้างอิง (test vectors) รูปแบบใดรูปแบบหนึ่ง:

-   PRNG ควรได้รับการทดสอบเทียบกับเวกเตอร์อ้างอิงมาตรฐานเมื่อมีให้ใช้งาน ([ตัวอย่าง](https://github.com/rust-random/rngs/blob/master/rand_xoshiro/src/xoshiro256starstar.rs#L122))
-   อัลกอริทึมอื่นๆ ควรมีเวกเตอร์ทดสอบของตนเองบรรจุไว้ในการทดสอบ
    `value_stability` หรือชุดทดสอบที่เทียบเท่ากัน ([ตัวอย่าง](https://github.com/rust-random/rand/blob/master/src/distr/bernoulli.rs#L226))

## การรองรับเวอร์ชันก่อนหน้า

เรามุ่งมั่นที่จะสนับสนุนผู้ใช้งานเครต `rust-random` ที่ยังคงใช้เวอร์ชัน `MAJOR.MINOR` ก่อนหน้า เพื่อประโยชน์ในการทำซ้ำผลลัพธ์ โดย:

-   จัดเตรียมแพตช์แก้ไขช่องโหว่ด้านความปลอดภัยในเวอร์ชันแพตช์ตามความเหมาะสม
-   ช่วยอำนวยความสะดวกในการพอร์ตฟีเจอร์เพิ่มเติมที่เข้ากันได้ย้อนหลัง (back-porting) จากเวอร์ชันในอนาคตกลับมาให้ *เมื่อมีการร้องขอ*
-   การแก้ไขข้อผิดพลาดอื่นๆ อาจได้รับการพิจารณาพอร์ตย้อนกลับเป็นรายกรณี แต่หลายครั้งก็ไม่สามารถทำได้โดยไม่กระทบต่อโครงสร้าง API หรือค่าผลลัพธ์เดิม

## ข้อจำกัด

### ความสามารถในการพอร์ตของ usize

น่าเสียดายที่ภาษา Rust มีสิ่งหนึ่งที่เป็นข้อจำกัดเรื่อง portability ซึ่งฝังลึกอยู่ในแก่นของภาษา นั่นคือชนิดข้อมูล `usize` (และ `isize`) ตัวอย่างเช่น ขนาดของ `Vec` ว่างจะแตกต่างกันระหว่างระบบ 32 บิตกับ 64 บิต สำหรับงานทั่วไปสิ่งนี้ไม่ใช่ปัญหา แต่สำหรับการสร้างเลขสุ่มที่ต้องการผลลัพธ์ตรงกันข้ามแพลตฟอร์ม เรื่องนี้ถือเป็นเรื่องสำคัญอย่างยิ่ง

จึงมีกฎง่ายๆ ที่ควรปฏิบัติคือ: หากต้องการให้โค้ดสามารถพอร์ตข้ามแพลตฟอร์มได้ *ห้าม* สุ่มค่าชนิด `usize` หรือ `isize` โดยตรงเป็นอันขาด

ตั้งแต่ `rand v0.9` เป็นต้นมา ชนิดข้อมูล `isize` และ `usize` จะไม่ได้รับการรองรับในหลายส่วนของ API สาธารณะ รวมถึงใน [`StandardUniform`] แต่ชนิด `usize` ยังคงได้รับการรองรับผ่าน [`SampleUniform`] และเมธอด [`Rng::random_range`] โดยระบบจะใช้วิธีการสุ่มแบบ `u32` ทุกครั้งที่เป็นไปได้เพื่อเพิ่มความสามารถในการพอร์ตให้สูงสุด

### ความสามารถในการพอร์ตของทศนิยม

ผลลัพธ์จากการคำนวณเลขทศนิยม (floating point) ขึ้นอยู่กับโหมดการปัดเศษและรายละเอียดเชิงลึกของขั้นตอนวิธีในแต่ละฮาร์ดแวร์ โดยเฉพาะผลลัพธ์จากฟังก์ชันอดิศัย (transcendental functions เช่น sin, cos, exp, log) มักจะมีความแตกต่างกันเล็กน้อยในแต่ละแพลตฟอร์ม ด้วยเหตุนี้ ผลลัพธ์จากการแจกแจงใน `rand_distr` ที่ใช้ชนิดข้อมูล `f32` หรือ `f64` จึงอาจไม่สามารถพอร์ตได้สมบูรณ์แบบ 100%

เพื่อลดปัญหาความแตกต่างดังกล่าว (หรืออาจเพิ่มความซับซ้อนขึ้นในบางมุม) เราจึงเลือกที่จะใช้การอิมพลีเมนต์ฟังก์ชันอดิศัยเหล่านี้จาก `libm` แทนไลบรารี `std` โปรดดูรายละเอียดเพิ่มเติมที่ [ฟีเจอร์ของ rand_distr](crate-features.html#ฟีเจอรของ-rand_distr)
